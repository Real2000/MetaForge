## 一、限流 / 配额生效性（429 语义实证）

**方法**：独立压测实例（隔离库、端口 35921），同 IP 对 `POST /api/auth/login` 连击 12 次
（错误凭据）。

**结果**：双层防线分层正确，语义完整——

| 请求数 | 响应 | 说明 |
|---|---|---|
| 第 1~4 次 | HTTP 200 + `code:401`「账号或密码错误（还剩 N 次尝试机会）」 | 账号级失败锁定前置（P5.x）：5 次错→锁 15 分钟 |
| 第 5~10 次 | HTTP 200 + `code:401`「账号已被锁定，请 15 分钟后再试」 | 账号锁定生效（第 5 次起） |
| 第 11~12 次 | **HTTP 429 + `code:429`「登录尝试过于频繁，请 1 分钟后再试」+ `retry_after: 60`** | **IP 级限流（10 次/分钟）生效；429 状态码 + retry_after 客户端友好语义完整** |

**结论**：账号级锁定（401 域）与 IP 级限流（429 域）分层清晰；`retry_after` 字段支持客户端退避。
`rate-limit.js` 的 XFF 伪造防护（AGENT_TRUST_PROXY 缺省不采信）与滑动窗口实现此前已过安全回归，
本轮为 V1.1 口径的行为级实证补全。**达标**。配额生效性（quota 429/403 语义）由 PG 轨道 e2e
持续覆盖（MT-13 订阅配额/BE-B3 日配额 29/29 全绿），不重复压测。

## 二、PG 模式并发写（MVCC）压测

**方法**：专用表 `ops_bench`（100 字节/行，测后按数据最小化清理）；两形态对照 5 秒——
A. **桥路径**（生产真实写路径）：`db.prepare INSERT` 循环（同步桥主线程串行语义）；
B. **PG 原生**：pg Pool 多连接并发 INSERT（绕桥，MVCC 真并发）。

| 形态 | 并发 | 实测 QPS |
|---|---|---|
| A. 桥路径（业务真实） | 1（主线程串行） | **643** |
| B. PG 原生 MVCC | 4 连接 | 3333 |
| B. PG 原生 MVCC | 8 连接 | 4778 |
| B. PG 原生 MVCC | 16 连接 | **5434** |

**解读**：

1. **桥串行化是 PG 模式写吞吐的形态瓶颈**（643 vs 5.4k，约 8 倍差距）——同步桥 callSync
   一次一条语句（含 RLS 上下文往返），多写者经业务层被串行化。**当前业务完全够用**：
   生产现状写入峰值（对话消息 + 审计 + 日志，人均 <1 QPS）距 643 QPS 有两个数量级余量
   （对照 B2 结论：数百人规模读写余量巨大）。
2. PG 原生多连接 16 连接 5434 QPS 为本机 Docker 容器口径（逐条自动提交含 WAL fsync，
   ~3ms/提交主导）——**无 sqlite 式单写者天花板**（MVCC 多写者吞吐随连接数线性增长至 fsync 饱和）。
3. **优化触发条件（记录，不立项）**：业务写峰值逼近 500 QPS 时，桥批量写管道
   （PG-2 时判定「冷启动已达标非必需」的项）重估——同步桥的串行语义届时成为瓶颈。
