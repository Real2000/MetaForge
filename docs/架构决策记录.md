# 架构决策记录（ADR）

> 对应《MetaForge 开发计划表 v1.0》「五、关键风险与决策点」的用户拍板项。已定决策落此归档，后续变更须新增条目而非改写历史。

## D-1 · 租户边界模型 —— ✅ 已定（随 M1 落地，2026-11-22）

**决策**：客户 = 独立租户（tenants 一等实体，默认租户 id=1）；`spaces` 降级为**租户内协作软分组**，不复用为租户边界。

**落地**：`tenants` 表 + 全资源 `tenant_id` 硬边界（fail-closed）；`space-utils` 两段过滤（先租户后空间）；平台超管可跨租户。私有化单租户部署下全部数据 `tenant_id=1`，行为与旧版一致。

## D-2 · 是否长期上 PostgreSQL —— ✅ 已定（2026-11-23 拍板：双模式，不做一刀切）

**决策**：**保留双数据库模式，按部署档位选择**：

| 部署档位 | 数据层 | 理由 |
|---|---|---|
| **私有化交付 / 单机部署（默认）** | **SQLite**（better-sqlite3） | 「解压即用、零运维」是私有化卖点：无数据库进程、无连接配置、拷文件+litestream 即备份；2C4G 小盒子可跑；离线信创包不增重 |
| **SaaS / 多机 / 高并发档位** | **PostgreSQL**（或金仓 KES，pg 协议） | 跨机共享写（SQLite 不可行）、RLS 行级租户隔离下沉 DB 层、消灭 SQLITE_BUSY、支撑多副本无状态横向扩容；`pgvector` 可作为向量索引的该档位继任者 |

**对计划表的影响**：
- `MT-7（数据层迁 PostgreSQL，8~12 人日）` 保留立项，但定位为 **SaaS 档位任务**，不阻塞私有化交付路线；
- `BE-C1（DAL 收敛）` 的投入优先级随此决策下调为「增量推进」——SQLite 档位下收益为可迁移性而非当期性能，lint 门禁维持零增长即可，批量替换按需排期；
- 性能基线报告的既有结论得到确认：「多机部署需求或日活 >5 万时才立项 PostgreSQL 适配层」（DAL/方言层已就绪，预估 3~5 人日适配 + 8~12 人日迁移）。

**实施要点**（MT-7 立项时执行）：连接池 + 关键表 RLS（tenant_id）+ 热点查询经 `lib/dal.js` 收敛 + FTS5→PG 全文检索降级链；部署侧 docker-compose 增加 pg 服务与启动顺序依赖，离线信创包走金仓（`AGENT_DB_DRIVER=kingbase` 已支持）。

## D-3 · 对外 API Key 全域模式 —— ✅ 已定（2026-11-23 拍板：需要全域模式，已落地）

**决策**：实现全域 Key——一个 Key 可访问**本租户全部已发布智能体**（企业对外集成场景：外部系统一 Key 集成多智能体），与现有「单智能体绑定 Key」并存。

**落地要点**：
- schema（迁移 #132，重建表法）：`agent_api_keys.agent_id` 可空（NULL=全域）+ 新增 `owner_username`（创建者，审计归属）/`tenant_id`（作用域边界）两列；存量绑定行归属自动回填（继承其智能体的 owner/租户）；
- 作用域防线（openapi.js authKeyForAgent，fail-closed）：全域 Key 仅可访问**同租户且已发布**的智能体——目标不存在/未发布拒绝、多租户跨租户拒绝（单租户 tenant_id 恒等零回归）；
- 管理端点从严：`adminOnly`（租户管理员/平台超管），列表/操作按 Key.tenant_id 隔离，非本租户 Key 视同不存在；
- Key 前缀 `sk-gk-`（与智能体级 `sk-ap-` 区分，泄漏排查可辨识）；SEC-02a 哈希存储语义不变；
- 前端：「智能体管理 → API 发布」弹窗新增全域密钥区块（创建/启停/删除，非管理员不显示）。

历史注记：M0/SEC-02a 时代「无绑定 Key」曾被判死代码移除（`agent_id NOT NULL`、生产库 0 行，当时 D-3 未拍板）——本次拍板后按上表设计完整恢复并补齐归属防线，无迁移包袱。

## D-4 · 向量库技术路线 —— ✅ 已定（2026-11-23 拍板：SQLite-vec，已落地）

**决策**：AI-02 收尾采用 **SQLite-vec**（vec0 虚拟表，库内 C 暴力 KNN），落库 `lib/vector-index.js`。

**依据**（10 万分块 × bge-m3 1024 维实测）：
- 现状真实路径（BLOB 传输 + 逐元素解析 + JS 扫描）p50 ≈ 1559ms / p95 ≈ 1904ms——超验收线（P95<300ms）5 倍+，瓶颈在**每次查询 400MB 向量搬运**而非算力；
- sqlite-vec KNN p50 ≈ 194ms（8 倍提升，数据不出库）；**精确暴力非近似**，「ANN 命中率 ≥98%」验收天然 100%；
- 信创友好：单一 C 扩展、npm 预编译覆盖 mac/win/linux(x64+arm64)、LoongArch 可自编译；与 better-sqlite3 同库，备份/主从故事不变。

**否决项**：LanceDB/专用 ANN（LoongArch 无预编译、Rust 工具链不可自编译，信创阻塞；仅 100 万+ 分块规模才需要）作为远期可插拔选项保留。SaaS 档位如走 PG，`pgvector` 经同一检索门面替换。

**实施**：`96409fc`（覆盖度闸 + 双写回填 + KNN 快路径 + 五处失效钩子 + 降级链 0 阻断）。运维开关：`AGENT_VEC_INDEX=0` 强制全表扫描。
