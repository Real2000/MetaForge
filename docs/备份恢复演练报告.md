## 一、双轨设计（ops.js）

| | sqlite 轨（既有） | PG 轨（本轮新增） |
|---|---|---|
| 触发 | scheduler 每日 03:30 → dailyBackup() | 同左（方言分支进 dailyBackupPg） |
| 机制 | `VACUUM INTO`（在线一致性快照，WAL 安全） | `pg_dump -Fc`（custom 格式：内建压缩 + 文件头自校验 + 排除表选项） |
| 产物 | `platform-YYYY-MM-DD.db` | `platform-YYYY-MM-DD.dump` |
| 排除表 | P1-22（临时库 DROP 后快照） | `--exclude-table-data=`（结构保留、数据排除；表名过标识符白名单） |
| 保留 | backup_keep（默认 30 份） | 同左（.dump 后缀独立计数） |
| 失败语义 | err_logs + 返回 {ok:false} | 同左（PG 轨为主备份，无降级语义——失败即真失败） |

**执行链设计要点**：

1. **命令来源**：config `backup_pg_cmd`（占位符 `{user}` `{db}`）自定义优先；缺省走
   `docker exec <容器> pg_dump -U postgres -Fc <db>`（容器内 pg 与服务端同源零版本错配；
   容器名 `AGENT_PG_CONTAINER` 显式 > `docker ps` 按 5432 端口自动识别）。
2. **超户而非业务角色**（演练实证的硬约束）：PG-1 的 **FORCE RLS 对 owner 也强制**——
   业务角色 pg_dump 直接报错 `query would be affected by row-level security policy`；
   备份窗口临时 NO FORCE 会造成 RLS 失效风险（不取）。postgres 超户天然 BYPASSRLS，
   只读 dump 动作 + 恢复侧 `--role=<业务角色>` 归属对齐；备份产物含全租户数据本就是备份语义。
3. **注入面收敛**：命令拆参数数组执行（execFileSync），非 shell 拼接。

**对账结果**：125 表全部恢复；行数 100341 全等；内容哈希 **0 不一致**。

**对账工程细节（复现踩坑，演练脚本已固化）**：
- 对账连接必须 `SET app.tenant_id='platform'`——FORCE RLS 对直连同样生效，首轮无上下文
  COUNT 被 RLS 滤光、「空对空」假一致；
- `op_logs/err_logs` 审计表按**时序前缀白名单**比对：dailyBackup 先 dump 后写审计行，
  恢复库天然是源库前缀（备份时点后的新审计行不算不一致）。

**RPO 口径**：每日 03:30 调度（scheduler 内置，不依赖外部 cron）→ **RPO = 24h**；单次备份为
MVCC 一致性快照（pg_dump 快照隔离），**任意备份产物内部零部分提交**。

## 三、恢复手册（runbook 联动）

PG 模式灾难恢复（详见 docs/PG切换runbook.md 回滚预案节，本节为备份产物恢复路径补充）：

```bash
# 产物：data/backups/platform-YYYY-MM-DD.dump
docker cp data/backups/platform-<date>.dump <PG容器>:/tmp/restore.dump
docker exec <容器> psql -U postgres -c "CREATE DATABASE <恢复库名> OWNER <业务角色>"
docker exec <容器> pg_restore -U postgres -d <恢复库名> --no-owner --no-privileges --role=<业务角色> /tmp/restore.dump
# 校验：SET app.tenant_id='platform' 后按 §二 对账口径（表数/行数/抽样哈希）
```

sqlite 轨恢复：备份文件本身即完整库（`better-sqlite3` 直开或替换 data/platform.db 后重启）。
